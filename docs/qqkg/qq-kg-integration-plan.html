5.3 插件兜底路径实证（2026-08-30 修正：headless 下不可用）

源码实证：audioSource.ts:77-95 的 resolveByPlugin 依赖 usePluginsStore()——插件注册表来自 Electron 主进程的文件系统扫描（src/ 下不存在插件加载目录，git 实证）。headless web 模式下 plugins.list 恒为空 → candidates.length === 0 → 直接返回 NO_PLUGIN_AVAILABLE。结论：插件兜底在 headless 是死路径，S3 官方接口直连是 QQ/酷狗在线播放的唯一可行方案。

这也反证了本计划的必要性：不做 S3，QQ/酷狗搜索登录做得再好，点击播放只会得到"无可用插件"错误。做 S3 的价值 = 官方接口直连 + 支持 VIP 音质（flac/hires 档位）+ 不依赖任何 Electron 生态。

6.2 为什么前端可以零改动（翻译层设计的关键）

前端各适配层（src/apis/search/qqmusic.ts:24 等）读取的是桌面端 Electron 的规范化格式 {code:200, total, songs}。本计划把翻译层放在 Rust 侧（headless 独有文件），让 headless 后端直接输出与桌面端一致的规范化格式——前端代码自然工作，无需任何修改。这是"后端适配前端"而非"前端适配后端"，从根本上避免了触碰上游文件。

6.3 上游同步流程（每次 merge 前的例行检查）

git fetch origin
git log dev..origin/dev --oneline          # 看上游新增提交
git diff dev..origin/dev --stat            # 确认改动文件与本计划文件无交集
git merge origin/dev                        # 本计划文件上游不存在，永不冲突
# 哨兵验证（上游改了前端读取格式时在此暴露）
pnpm typecheck:web
# 接口回归（S1/S2/S3 验收 curl 各跑一遍）
bash scripts/deploy-headless.sh
上游若修改了 src/apis/search/* 的字段读取（如 songs → items），merge 后 typecheck 或搜索回归测试会立即暴露——此时只需调整 Rust 翻译层的输出格式（独有文件），依然零冲突。

8.2 与 HIFI 主线的协同

  • 本计划全部改动不触碰音频信号链（decoder/equalizer/tempo 零接触），与 bit-perfect 主线完全正交；且纯 Rust 约束与 HIFI 定位天然一致——在线解析（MD5/RSA/3DES）均在 Rust 进程内完成，无跨语言桥接开销
  • QQ/酷狗在线音源在 HIFI 定位下是"补充音源"，但插件兜底已实证不可用（5.3）——若 QQ/酷狗要能播放，S3 是唯一路径，不存在"暂缓不做还能凑合"的选项
  • 实施顺序建议：P0（stop panic）→ S1 → S2 → P1（bit-perfect）→ S3-酷狗 → S3-QQ（QQ 播放需求存在则必做，3DES 移植 ≈8h）
