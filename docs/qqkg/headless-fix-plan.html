一、方向调整说明（v1 → v2 → v3）

v1 计划的目标是"把桌面版功能补齐到 headless"。用户定位变更：headless 模式打造为极致 HIFI 专用形态——信号从文件比特到 DAC 比特零加工（bit-perfect）。因此大量 v1 修复项转为"反向裁剪"。v3 新增 P4：QQ/酷狗登录链路打通——设置页有 UI 入口但登录按钮全链路未实现。

v1 计划项v2 决策理由
P0 stop 接口 panic 修复保留稳定性前提，与音质方向无关
P1 补全 DSP API（速度/音调/EQ/均衡/淡入淡出 9 条路由）取消 → 前端隐藏每一项都是信号加工：Biquad 滤波改频响、时间拉伸有损、限幅/均衡/淡出改增益——与 bit-perfect 直接冲突
P2 输出设备列表 API简化固定 HIFI 系统（Diretta Target + 固定 DAC），现有 Diretta 面板已够用
P2 stats 汇总修复取消行为统计与听音无关；play_history 保留（歌单"最近播放"依赖）
P3 FFT 频谱可视化取消与听音无关，还要求开 fft feature + 解码侧多一条重采样支路；维持 default-features = false
P4 次要功能（cover_raw / deleteTracks / 歌词文件）搁置与 HIFI 无关，需要时再做
（新增）数字音量控制反向处理音量 < 1.0 的 f32 乘法等效损失位深（-20dB 约丢 3.3 bit），锁 1.0，音量交给 DAC/Diretta 模拟端

硬约束（2026-08-30 新增，已四项实证达标）：headless 后端必须纯 Rust 实现，禁止引入 Node 运行时依赖。运行时形态 = 单一 Rust 二进制 + 静态 web 资源；Node 工具链仅允许构建期（pnpm build）。实证：① Rust 代码零 Command::new 子进程调用；② 运行进程仅 /opt/splayer-headless/splayer-headless，无 node；③ /opt 目录无 node_modules；④ 依赖栈全 Rust（axum/tokio/reqwest/rusqlite-bundled/md5/ncm-api-rs 纯 Rust crate）。对后续实施的含义：任何新功能（QQ/酷狗解析的 MD5/RSA/3DES、歌词、元数据等）一律用 Rust crate 在 headless 独有文件中实现，禁止 spawn node、禁止复用 Electron TS 代码运行时、禁止引入 npm 包侧车服务。桌面端 TS 实现只作移植参考。

既有冲突面提醒（历史遗留，非本计划产生）：当前 dev 相对 origin/dev 已有约 33 个文件存在内容差异（src/main.ts、src/services/playback.ts、src/stores/library.ts、src/utils/quality.ts、shared/types/*.ts 等，系此前 headless 适配所改）。这些是当前 merge 时真正的冲突处理点，建议后续有机会逐步收敛：将其中可迁移的逻辑挪入 headless 独有文件，差异面越小火花越小。本计划所有新增改动不再扩大此差异面。

三、P0 · 切歌 panic 修复

0
stop 接口隔离
≈ 0.5 小时

现状：前端切歌先调 stop，headless-server 的 stop_handler（routes.rs:408）在 tokio worker 上直接执行 player.stop()，drop 内嵌 Runtime 的 HttpAudioSource 时触发 panic；与 load 竞争时会杀死新曲目（已实测复现：一次静音 4 小时）。

async fn stop_handler(State(state): State<AppState>) -> Result<Json<PlayerResponse>, ApiError> {
    let player = state.player.clone();
    // 与 load/seek 一致：独立线程 drop 解码器，避免内嵌 Runtime panic
    let result = spawn_isolated_blocking(move || {
        player.lock().stop()
    }).await;
    ...
}

仅改 stop_handler 一个函数体。验证：连续切歌 20 次 journalctl | grep -i panic 零输出；在线曲播放 30 分钟无中断。

四、P1 · bit-perfect 直通模式（核心新增）

1
服务端直通开关 + DSP 链全旁路
≈ 1.5 小时

重大利好（已源码核实）：直通所需的大部分旁路逻辑引擎里已经有了，本阶段主要是"把现有开关组合成一个模式"：

  • EQ：equalizer.rs:199 — if !self.enabled { return; } 禁用时完全旁路，零信号改动
  • 变速变调：tempo.rs:62 is_bypass() — speed=1.0 且 transpose=0 时整段跳过（decoder.rs:323 已接此判定）
  • 音量均衡 / 淡入淡出 / 数字音量：均有现成 setter 可归零

4.1 API 设计（新文件 player_ext.rs）

GET  /api/v1/player/bitperfect          // → { enabled, sample_rate, channels }
POST /api/v1/player/bitperfect          // { "enabled": true } → 应用并返回状态

4.2 开启时执行的 setter 组合（全部现成）

player.set_equalizer_enabled(false);     // EQ 全旁路（equalizer.rs:199 生效）
player.set_speed(1.0);                   // 触发 tempo is_bypass（tempo.rs:62）
player.set_pitch(0);
player.set_normalization_enabled(false); // 响度均衡关闭
player.set_fade_duration(0);            // 无淡入淡出包络
player.set_volume(1.0);                  // f32×1.0 位级无损

4.3 锁定语义（新增的少量代码）

  • bit-perfect 开启时，AppState 记录 bit_perfect: AtomicBool；所有 DSP 类写请求（若未来接入）返回 409 "bit-perfect mode active"，防止误操作破坏直通状态
  • 音量接口在直通下同样返回 409（前端音量条已隐藏，此处是兜底）
  • 持久化到 config.yaml（bit_perfect: true），服务重启自动恢复

4.4 需要验证/小改的一个点：输出限幅器

decoder.rs:324 显示 stretch 旁路路径仍会过 limiter.process()。恒定增益下限幅器理论上 bit-identical（×1.0），但需验证其是否有 lookahead 延迟或攻击包络。验证方法见第七节 bit-compare 测试；若对比不一致，在 process_audio_chunk 加一个直通短路（if shared.is_bit_perfect() { return chunk; }，Shared 上加 AtomicBool，约 5 行）。

4.5 数据面事实说明（写进文档供参考）

  • 内部管线是 f32（24-bit 尾数）：16/24-bit 整数 PCM → f32 → DAC 数值无损，不存在精度损失
  • 本地输出按音源原始采样率打开设备（已实现）；Diretta 只接受 44.1k 系列（44.1/88.2/176.4/352.8k），48k 音源会在解码侧重采样——选音源优先 44.1k 系无损

7.4 边界说明（与 HIFI 方向的关系）

P4 只打通登录态（认证 + 资料 + 会话持久化）。QQ 的 song_url（vkey 机制）、酷狗 VIP 音质解析属于"在线音源补全"，涉及 3DES/sign 更多移植，不在 P4 范围——是否做取决于是否需要 QQ/酷狗作为在线音源（当前 HIFI 主音源是本地 + 网易云）。登录打通后这些能力可随时增量补充。

八、保留清单（HIFI 本体，一个不动）

  • 解码全家桶：DSD（DSF/DFF）、SACD 含 DST 解压、MQA、HDCD、CUE、ffmpeg 全格式、DTS
  • 原始采样率直出：按音源原始率打开输出设备（已实现）
  • Diretta 推流：网卡绑定、Tokio 线程隔离、rt 调度、300ms 预填、watchdog——上周刚调优完的 HIFI 关键路径
  • 网易云在线音源：保留；建议账号内锁定无损/Hi-Res 音质，选源优先 44.1k 系（Diretta 约束）
  • 歌词与封面：不碰信号链，听音体验保留
  • play_history 轻量记录：歌单"最近播放"依赖

九、验证与部署流程

9.1 bit-compare 终极验证（P1 的验收标准）

# 1. 用 ffmpeg 解码同一文件得到参考 PCM
ffmpeg -i test.flac -f f32le -ar 44100 ref.pcm
# 2. 开启 bit-perfect，播放同一文件，从输出侧抓取管线 PCM
#    （临时验证路由 GET /api/v1/player/dump_pcm，验证后删除）
# 3. 比对
cmp ref.ppm captured.pcm && echo "BIT-PERFECT OK"

比对不一致时按 4.4 节排查限幅器，加直通短路后复测。此测试同时覆盖"EQ 禁用是否真零改动"的验证。

9.2 常规验证与部署（每阶段）

cargo check -p audio-engine-core --no-default-features   # headless 裁剪态
cargo check -p audio-engine-core -p headless-server       # 默认态 + 服务端
